# Teach the harness to click and type

LLM OS's VM tests never touch the layer a real person uses. No harness sends a hardware-level click or keystroke into the guest. "Typing" means `llmos say` calling `Desk.say` directly, "button presses" go through `desk-ctl act '<words>'`, and screendumps are saved but never checked ([llmos_harness_audit §2, §6](../research_notes/VM%20real%20use%20testing%20plan/llmos_harness_audit.md)). That leaves the WebKit page, labwc's pointer and keyboard routing, focus, Enter handling and the page-to-Python bridge with no tests at all. A recorded false positive came from exactly that blind spot: a host mock of `app_press` hid a first-run-wizard bug ([queue.md:15](../../tasks/queue.md)). The fix is cheap, because the guest already has `virtio-tablet-pci` and `virtio-keyboard-pci` attached ([boot-target.sh:43](../../../tools/boot-target.sh)). It is missing only a QMP socket, plus a way for the desk page to report where its elements are. The orchestrator should therefore spend its next rounds on three phases. **Phase 1** builds real input and screen capture, and its gate is one proven click-type-Enter round trip through `#in`. **Phase 2** turns the existing 50-case basic sweep into a JSON task suite graded by real system state and calibrated against the hand verdicts already on file. **Phase 3** adds repeat runs, flake classification and a signature-based triage loop that feeds ranked FIX tasks back into the queue. The plan at the end splits this into 35 small Haiku-sized tasks. Each one names its files and the check that proves it worked.

## Every current harness drives handlers, not the screen

The audit read every harness and found one pattern. Boot goes through `boot-target.sh` with hvf, `-display none` and an HMP monitor. Commands go as text over the serial line. Desk actions go through the desk's control socket ([boot-target.sh:38-48](../../../tools/boot-target.sh)). Grepping `tools/` and `src/` for `qmp`, `sendkey`, `input-send-event`, `xdotool` or `ydotool` returns nothing, and no QEMU invocation has `-qmp` or `-vnc` ([audit §2](../research_notes/VM%20real%20use%20testing%20plan/llmos_harness_audit.md)). The control socket's `say`, `act`, `wizard` and `dialog` commands call Python methods directly. `dialog` answers **every** pending confirmation with one value, and `js` only emits an `eval` to the page and returns `{"ok": True}`, so a test cannot read any value back from the DOM ([desk.py:4046-4134](../../../src/rootfs/usr/lib/llmos/llmos/desk.py)).

Grading is the second weakness. `usecase-run.py` asserts nothing and saves results "for review against 'success looks like'" ([usecase-run.py:5](../../../tools/usecase-run.py)). `button-sweep.py` counts a button as ok if any window or the reply changed ([button-sweep.py:51-53](../../../tools/button-sweep.py)). `calc-smoke.sh` matches reply substrings ([calc-smoke.sh:58-84](../../../tools/calc-smoke.sh)). Timing is coarse too. 64 of 93 use-case timings round to 9 s because of the runner's fixed `sleep(4)` loop ([usecase-run.py:65-70](../../../tools/usecase-run.py)), so a 0.5 s reply and an 8 s reply look the same. Configuration is the third weakness. `testreset` forces `autonomy balanced`, `screen_off 0` and `autolock 0`, so every test runs in a configuration no owner has ([desk.py:4106-4121](../../../src/rootfs/usr/lib/llmos/llmos/desk.py)). There is no separate "simulator" to fall back on. The host-side fakes are themselves the recorded source of false confidence, and they cannot stand in for VM truth. The latest fully hand-graded VM run was the 1.7.1 basic sweep: **43 of 50 passed outright**, two real defects (S40, S48) were fixed, and the rest were start-up races, which a hand follow-up was needed to tell apart ([basic-sweep.md:59-91](../basic-sweep.md)). Builds 1.7.2 through 1.7.5 have had only calc-smoke and timed-sweep coverage.

Some notes need correcting against what this checkout actually contains. The guest compositor is **labwc**, not sway ([rc.xml](../../../src/rootfs/etc/xdg/labwc/rc.xml)), so sway `input` blocks and `swaymsg` do not apply. The host QEMU is **11.1.1** (`qemu-system-aarch64 --version`). The image has **no qemu-guest-agent**. **qemu-nbd is installed but guestfish is not**, and macOS has no NBD client, so "read the overlay from the host" has to be proven before anyone relies on it.

## QMP alone closes the click-type-see loop

QMP `input-send-event` has injected key, button and absolute-pointer events since QEMU 2.6. Absolute axes take values from **0 to 0x7fff**, and `query-mice` reports whether the active pointer is `absolute` ([QEMU qapi/ui.json](https://gitlab.com/qemu-project/qemu/-/raw/master/qapi/ui.json)). Since QEMU 7.1, `screendump` takes `"format":"png"` ([QEMU commit 9a0a119a](https://qemu.googlesource.com/qemu/+/9a0a119a382867dc9a5c2ae9348003bf79d84af2)). A 7.1.0 build segfaulted after a PNG screendump sent through **HMP** ([QEMU issue #1210](https://gitlab.com/qemu-project/qemu/-/issues/1210)), so capture should go through QMP. Host-side events pass through the guest's whole kernel input stack. That makes them more faithful than in-guest `wtype`, which injects at the compositor, or than AT-SPI and WebDriver, which skip input altogether ([wtype README](https://github.com/atx/wtype); [ydotool README](https://github.com/ReimuNotMoe/ydotool)). The design rule follows: **act through QMP, assert through state**.

Typing needs care. QMP sends key codes, not characters, so the harness needs its own US character map, with uppercase letters and symbols wrapped in shift. Each key needs a separate down and up event, with a pause between them. openQA, the largest user of this approach, still drops characters under load. It mitigates this with rate limits and by waiting for the screen to change every ~30 characters ([openQA testapi](https://open.qa/api/testapi/); [progress #12250](https://progress.opensuse.org/issues/12250?tab=notes)). The research marked the exact punctuation spellings in QKeyCode as unverified, so the first RUN should read them from the live `query-qmp-schema` before anyone writes the map. One adopter of the tablet saw clicks land with a vertical offset ([pmbootstrap f602df01](https://git.syndicate-lang.org/synit/pmbootstrap/commit/f602df01406fe8b1717aeaeb07bbb2d4118d6953)). The gating test therefore has to measure where a click actually lands. If virtio-tablet misbehaves under labwc, the fallback is `qemu-xhci` with `usb-tablet`, the device QEMU's own aarch64 graphical config uses ([mach-virt-graphical.cfg](https://qemu.googlesource.com/qemu/+/fbd3c4cff641cae082edb765017cbb699efa6712/docs/config/mach-virt-graphical.cfg)).

To click something by name, the harness needs its coordinates. OCR of the desk is known to give false hits on the desk's own UI ([queue.md:81](../../tasks/queue.md)). The desk is a single WebKit view, so the cheapest reliable locator is the page itself. A test-shell-gated control command should evaluate a selector and send back `getBoundingClientRect()`, `devicePixelRatio` and the viewport size. Pixels then convert to the 0..0x7fff range using the size of the current screendump. WebKitWebDriver is a heavier alternative. It needs `set_automation_allowed` on the web context, and only one context can have it ([WebKitGTK docs](https://webkitgtk.org/reference/webkit2gtk/stable/method.WebContext.set_automation_allowed.html)). The rect read-back covers the need with one small handler.

For waiting, the proven pattern is to **wait for a change, then wait for stillness**: poll frames until they differ from the "before" frame, then until N consecutive frames are nearly identical, with a timeout on each step ([openQA testapi](https://open.qa/api/testapi/)). Playwright does the same before every comparison, and it hides the caret and disables animations ([Playwright snapshots](https://playwright.dev/docs/test-snapshots)). The desk also has a cheaper completion signal already: `desk-ctl wait` returns once nothing is running or queued ([desk.py:4062-4067](../../../src/rootfs/usr/lib/llmos/llmos/desk.py)). The runner should use both. `wait` decides when the agent has finished, and the frame-still check decides when the screen can be captured.

For reset, keep the qcow2 overlay plus cold boot that exists today. arm64 reaches the test shell in **14 s** ([queue.md:6](../../tasks/queue.md)). Live snapshots on Apple Silicon hvf have a reported revert crash on QEMU 11.0.1 ([QEMU #3565](https://gitlab.com/qemu-project/qemu/-/work_items/3565)), and nobody knows whether 11.1.1 has it. They belong in one late RUN, not on the critical path.

## Grade real state, and calibrate against verdicts already on file

Every serious GUI-agent benchmark grades the **final system state** with execution-based checks, not screenshots. OSWorld tasks are JSON with an `instruction`, setup `config` and an `evaluator` of `{func, result, expected}`. A typical evaluator runs `which spotify` in the VM and applies include and exclude rules ([OSWorld task JSON](https://raw.githubusercontent.com/xlang-ai/OSWorld/main/evaluation_examples/examples/os/94d95f96-9699-4208-98ba-3c3119edf9c2.json)). AndroidWorld checks app databases and settings over adb, and it treats UI matching only as a fallback ([AndroidWorld](https://arxiv.org/html/2405.14573)). macOSWorld lets the agent see the machine only through VNC and grades over a separate SSH channel ([macOSWorld](https://arxiv.org/html/2506.04135)). LLM OS reverses the roles: the harness becomes a scripted user and the OS's built-in agent does the work. No benchmark has done this before, but the grading pattern carries over unchanged.

Deterministic checks should gate, and an LLM judge should only flag runs for review. On AgentRewardBench's 1,302 expert-labelled trajectories, rule-based grading reached **83.8% precision** and no LLM judge exceeded **70%** ([AgentRewardBench](https://arxiv.org/html/2504.08942v2)). Graders also need their own audit. BenchJack found **219 flaws** across 10 benchmarks, including graders that read state the agent can change ([BenchJack](https://arxiv.org/abs/2605.12673)). LLM OS has no unprivileged-user split yet, so every in-guest getter (`tsh` over serial) can be reached by the agent and should be labelled that way. Host-side reading of the shut-down overlay would escape that problem, but it needs a RUN to prove it first. The candidate method is `qemu-img convert` to raw followed by e2fsprogs `debugfs`, because guestfish and NBD mounting are unavailable on this Mac. OSWorld-Verified's main lesson is that reliable rewards take more human effort than expected. Its biggest fixes went to evaluator false negatives and timing races, such as keys fired before Writer had finished loading ([OSWorld-Verified](https://xlang.ai/blog/osworld-verified)).

That points to the order of work. Start from the 50 basic-sweep cases, because they already have hand verdicts, and require the automatic grader to reproduce those verdicts before trusting it on anything new. Require "do nothing" and "reply Done" to score zero on every feasible task. Then run the same build twice, once through real input into `#in` and once through `llmos say`. **Any difference between the two runs is a page-layer bug** that no current harness can see. A pointer-driven button sweep, clicking by rect instead of `act`, catches the class the audit identified: dock-chip clicks route to an `app.focus` handler that is just `pass` ([parity-results.md:1294](../parity-results.md)). A later lane should keep the shipped settings, skipping the `testreset` overrides, so screen blanking, autolock and the real confirmation UI get exercised.

## Flakes are signal, but only after two runs

Most flakiness comes from timing. At Google, about **1.5% of runs** were flaky and **16% of tests** showed some flakiness ([Google Testing Blog](https://testing.googleblog.com/2016/05/)). Google reruns only tests that are marked flaky ([same post](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)). Microsoft warns that flaky failures can be real bugs. Its RootFinder tool finds causes by comparing logs from passing and failing runs ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/root-causing-flaky-tests-in-a-large-scale-industrial-setting/)). LLM output adds variance on top: AndroidWorld's agent scored **27.6, 26.3 and 33.2%** across three seeds ([AndroidWorld](https://arxiv.org/html/2405.14573)). With llama.cpp, temperature 0 or a fixed seed makes server output repeatable ([llama.cpp #4668](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/65e5f6dadbba4b496bba27f573e473c66b446496)), but the desk's current sampling settings are unknown, so a PROBE comes first. LLM OS has already been hurt by this. Back-to-back requests produced false failures on S32 and S35/S36 ([basic-sweep.md:83-91](../basic-sweep.md)), and a timed-out reply was read by the next phrase ([queue.md:57](../../tasks/queue.md)).

The policy for the orchestrator should be simple. Rerun a failure once on a fresh overlay. Pass then fail means flaky: file it, but don't let it block. Fail twice means real: dispatch a FIX. Every failure gets a signature of `task_id|step|assertion_kind|expected|normalized_error`, with digits, paths and PIDs stripped, and is hashed. N failures then collapse into K problems, ranked by severity × distinct runs affected, with an extra weight on paths owners use most. Each cluster carries a repro bundle: the last two screenshots, the step trace, the expected value, the desk log tail and a one-line rerun command. That bundle is what lets a Haiku FIX worker act without rerunning the suite. The Phase 1 log task must therefore confirm that desk.log is no longer empty on the VM ([queue.md:38](../../tasks/queue.md)). Suites must also be split to finish well inside the 3 h `vm-lifetime` guard ([vm-lifetime.sh:8](../../../tools/vm-lifetime.sh)). The last 93-case run took about 2 h 16 min.

## Conclusion

The cost is low. One QEMU flag, one host module and one test-gated desk command move LLM OS testing from "the handlers work" to "a person can do it". The real-input-versus-`llmos say` comparison then works as a standing oracle for page-layer bugs. What remains uncertain is narrow but decisive. Nobody has yet sent a virtio-tablet click through labwc into this WebKit view, and the outcome of P1-8 and P1-9 decides whether the virtio pointer path holds or the USB fallback is needed. Overlay grading from the host is unproven, so until a RUN proves it, every state check is agent-reachable and the suite should report it as such.


## Prioritized task plan for the orchestrator

**Conventions for every spec below.**
- **Paths and commands.** Paths are relative to the worktree root (`Support files/...`) and no task uses `cd`.
- **VM work is RUN work.** Any task that boots, touches or reads a VM or `run/` is a RUN. RUN tasks call `/bin/bash "/Volumes/Files/Claude Work Area/LLMOS/Support files/tools/<script>"` with the path written out, run strictly one at a time, and quit only `run/target.pid`. PROBE tasks only read source. `boot-target.sh` quits any VM on `run/tmon.sock`, so a PROBE that booted a VM would kill a running sweep.
- **FIX workers cannot see `run/`.** They run in worktrees reset to `llmos-1.5.0`. When a FIX needs a fact a RUN produced, the orchestrator pastes that fact into the FIX spec.
- **Image handling is stdlib-only**, like `screendump.py`. Poll with QMP `format: ppm`, which Python can parse without a PNG decoder, and save PNG only as an artifact. No PIL.
- **Shared files.** Two tasks that share a file never run in the same round. The marks are **B** = `tools/boot-target.sh`, **D** = `desk.py`/`index.html`, **R** = `tools/realrun.py`, **E** = `tools/evaluators.py`, **T** = `tools/triage.py`.
- **"After"** lists the tasks that must be merged or reported first.
- **Intent regexes** in any test include one contracted example (`what's`, `I've`).
- **Merging.** Each FIX is followed by a VERIFY of its branch, which runs the spec's test and every host suite, before merge.
